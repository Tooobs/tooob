# tooob

A semi-private web for people and their AI agents. Run something at home, or have your agent run it (Home Assistant, a folder of photos, a status dashboard, a dev preview), and let the people and agents you invite reach it in an ordinary browser: no port forwarding, no public URL, and nothing in between that can read the traffic.

A **Host** on your home box makes one **Site** reachable over [iroh](https://iroh.computer). A Visitor opens an **Invite Link**. Their browser loads a small static page, the **Bootstrap**, which connects to the Host through a **Relay** and then, when it can, straight to it over WebRTC. The Relay forwards encrypted traffic it can't read. Who may get in is decided only on the Host.

It's **private, not anonymous**: a Relay still sees which keys talk, when, how much and from where ([ADR 0007](docs/adr/0007-private-not-anonymous-no-public-ingress.md)).

**Status:** early. v1 is for technical early adopters on Linux and macOS. Expect the commands to change. [What you can try](#what-you-can-try) says what works so far, and [the roadmap](docs/roadmap.md) what comes next.

## What you need

**A Relay.** tooob names none of its own ([ADR 0015](docs/adr/0015-no-default-relay-or-bootstrap.md)), so you run one, or use one run by someone you trust. A Relay serves the Bootstrap too, so it's all a Host needs. [`deploy/`](deploy/README.md) has two setups, a VPS with Docker (`wizard.sh` walks through it) and Fly.io, and lists what a Relay needs: a domain of its own with a wildcard DNS record, an API token for that DNS, TCP 443 and generous bandwidth. As shipped, a Relay lets anyone use it until it has Enrolled Keys: `tooob-relay enroll <host key>` in its container before you share it (#128).

## Install

On macOS (Apple Silicon) or Linux (arm64, x86_64), a prebuilt `tooob`:

```sh
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/Tooobs/tooob/releases/latest/download/tooob-installer.sh | sh
```

It goes in `~/.local/bin`: open a new terminal, then `tooob --version`. To upgrade, `tooob upgrade`: it shows the newest Release and a link to its notes, asks before it installs it (through that Release's own installer, as above), and restarts the Hosts kept running (`tooob run NAME -d`) on it; Hosts you run by hand keep their Release until you restart them, and it names them. `--check` only looks, `--yes` doesn't ask (a script needs it), and `tooob upgrade 0.1.0` installs that exact Release, an older one too. It won't install a Release that would leave a Host on a Bootstrap Mismatch until its Relay serves that Release's Bootstrap (`--anyway` does it regardless), and it only replaces `~/.local/bin/tooob`: a `tooob` built from source, moved, or in a container is upgraded by hand. A running Host looks for a newer Release once a day and says so in its log and under `tooob ls`; `TOOOB_NO_UPDATE_CHECK=1` turns that off. Every Release's archives, checksums and notes are on [Releases](https://github.com/Tooobs/tooob/releases). The macOS binary isn't signed yet ([#52](https://github.com/Tooobs/tooob/issues/52)), so one downloaded in a browser won't run until you clear its quarantine: `xattr -d com.apple.quarantine tooob`.

## Build from source

```sh
cargo build --release                       # the tooob command: target/release/tooob
bootstrap/build.sh                          # the Bootstrap's WASM into bootstrap/www
```

`build.sh` needs the `wasm32-unknown-unknown` target, `wasm-bindgen-cli` at exactly the `wasm-bindgen` version in `bootstrap/web/Cargo.toml`, a clang that can target wasm (set `LLVM=` to its `bin/`; on macOS, Homebrew's `llvm`), and Node, which writes the Bootstrap Bundle's manifest, `www/__tooob/version.json`: its Release, its Protocol Version and every file's SHA-256. `node bootstrap/manifest.mjs --check bootstrap/www` says what no longer matches it, and `--hash` prints the Bundle's hash: its manifest's SHA-256.

## Use

```sh
tooob add photos ~/Photos --relay https://relay.example/
tooob run photos                            # in the foreground; Ctrl-C ends it
tooob run photos -d                         # or keep it running: launchd or systemd runs it, now and after logins, reboots and crashes
tooob stop photos                           # stop it; one kept running stays stopped until start
tooob start photos                          # start it again the way it ran: launchd or systemd runs it
tooob invite photos mom --expires 7d        # prints the Invite Link (https://<host key>.relay.example/#invite=…)
tooob visitors photos                       # who has got in
tooob invite photos aunt --approve          # a device it lets in waits until you approve it
tooob approve photos 482 917                # the Device Code that device shows, and visitors shows
tooob block photos <key prefix>
```

With `--approve` (and with `--owner`, for a device to become an Owner Device), the device that opens the link shows a **Device Code**, `482 917`, and `tooob visitors` shows the same code beside it. Ask the person who has the device to read you its code, and approve only when the two match: a link that's been forwarded, or opened by someone else first, shows a code you weren't told.

`TARGET` is a folder or file (served read-only, as a Shared Folder) or `HOST:PORT` for a web app. A Host's settings are a file you edit by hand (`tooob show photos` says where). Owner commands work whether the Host is running or not. `tooob` with no arguments lists every command.

Every Host writes its own log, however it's started, with the time on each line; a Host run in a terminal prints the same lines there. `tooob logs photos` shows the last 50 lines, `-n 200` or `-n all` more, `-f` follows it, and `--json` gives one object a line. A log rolls over at about 1 MB and keeps one older file, so it never fills a disk ([ADR 0025](docs/adr/0025-what-a-host-records-about-its-visitors.md)).

A Host never puts itself in the background ([ADR 0014](docs/adr/0014-hosts-run-in-the-foreground-the-os-keeps-them-running.md)): `tooob run photos -d` (`--detach`), or `tooob share PATH … -d`, hands it to your service manager (a launchd agent on macOS, a systemd user unit on Linux), which runs `~/.local/bin/tooob run photos` now and after logins, reboots and crashes, so a restarted Host runs the Release you last installed. Unlike Docker's `-d`, it outlasts a reboot. `tooob logs photos -f` follows it there too, `tooob stop photos` stops it and keeps it stopped, across logins and reboots, until `tooob start photos` hands it back to your service manager, as it ran before; `tooob ls` shows those as AUTOSTART `stopped`, and `tooob start` alone lists them. `tooob rm photos` stops it, removes its entry and deletes it. `share` on a Host that's kept running adds its Invites and prints them, without starting a second copy. `enable` and `disable` are gone: they're `run -d` and `stop`. While a Host serves, a Mac doesn't idle-sleep, but closing its lid still sleeps it. On a Linux box nobody stays logged in to, `loginctl enable-linger` keeps it running from boot. Without systemd or launchd, have your own service manager run `~/.local/bin/tooob run photos`, restarting it on failure.

An Invite Link, piece by piece ([ADR 0020](docs/adr/0020-a-relay-serves-its-bootstrap.md)):

```
https://kgjwugk89iaan7dtoyuju7pts5r7j3f1zxm3zp8k98nepg1hq46y.relay.example/#invite=00be5118…
        └──────────────────── Host Key ────────────────────┘ └── Relay ──┘  └── Invite ──┘
```

- **The Host Key**: the Host's identity and its address, made with the Host (`tooob show` prints it). It's in z-base-32, 52 characters, so it fits in a hostname. It isn't secret: who gets in is decided on the Host.
- **The Relay's domain**: the visitor's browser loads the Bootstrap from it, and reaches the Host through it.
- **Together, the Key Address** (`<host key>.<relay domain>`): each Host is an origin of its own, so no Site's scripts can reach another's browser storage or Visitor Key. It lasts as long as the Host Key and the Relay: a new Relay, or a deleted Host, means new Invites for everyone.
- **After `#`, the Invite**: browsers never send this part to a server, so the Relay never sees it. It works once, for one browser (another browser on the same phone or computer needs its own link), and the page drops it from the address bar once it's used.

Each of a Site's pages has its own address on the Key Address: `https://<host key>.<relay domain>/subfolder/` opens that page ([ADR 0023](docs/adr/0023-site-pages-have-real-paths-on-their-key-address.md)). Links within a Site work as they would anywhere, and the address bar and the tab's title follow the Site, so a reload, a bookmark or a shared link lands on the page it was.

- **[#116](https://github.com/Tooobs/tooob/issues/116) A Shared Folder can take uploads, add-only, when you turn them on** · 2026-11-04 · 0.3.4
  - `tooob share ~/dropbox --uploads --relay https://r.tooobs.net/ --invite jm` (or `uploads = true` in an existing Host's settings, read when it starts). In any folder's listing, jm gets an **Upload** button and can drop files onto the page: each shows its progress, and the listing refreshes saying the name each was saved as. Upload a name that's already there and it's saved as `photo (1).jpg`; nothing is ever overwritten, renamed or deleted. Try a name like `index.html` or `..` and the page says why it's refused; a folder that serves its own `index.html` takes no uploads. Each finished upload shows in `tooob logs` with who sent it, where and how big. Files in such a folder are served sandboxed, so an uploaded web page's script never runs. Off by default: without `--uploads` there's no button and the Host refuses uploads. Mind what you share: Visitors can add files anywhere in it except hidden folders, and from 0.3.5 never into your home folder (#121).
- **[#121](https://github.com/Tooobs/tooob/issues/121) Uploads never plant a file your machine runs: no hidden names, no home folder, never executable, quarantined on macOS** · 2026-11-06 · 0.3.5
  - `tooob share ~/drop --uploads --local` prints `Visitors can add files to any folder in ~/drop, except hidden ones`. From the page, try uploading `.zshrc`, or into a `.git/hooks` folder, or through a symlink inside the share that leads into one: each is refused with why, and nothing is written. A hidden folder's listing has no Upload button. `tooob share ~ --uploads` is refused, saying to share a folder inside it; a Host set up that way before starts read-only and says `uploads are off: ~ is your home folder; share a folder inside it` in its output, `tooob logs` and `tooob ls`. Upload a script or an app: `ls -l` shows it isn't executable, and on macOS `xattr -p com.apple.quarantine` shows tooob put it there, so Gatekeeper asks before it runs.
- **[#108](https://github.com/Tooobs/tooob/issues/108) Linux tests run before a Release is tagged, and on every push to main** · 2026-11-06 · the next Release (not out yet)
  - Nothing shows in tooob itself; this changes how it's checked. `./release.sh` now runs the Host's tests on Linux (`test/linux/run.sh`, in podman) before it tags, and refuses up front, saying `podman machine start`, if podman isn't running. Every push to `main` runs `cargo test` on x86_64 and aarch64 musl in CI: `gh run list --workflow linux-tests.yml` shows each push's result.
- **[#2](https://github.com/Tooobs/tooob/issues/2) A cancelled request stops the Host's request to the Site** · 2026-11-06 · the next Release (not out yet); live on r.tooobs.net now
  - Share a Site that long-polls (a chat, a dashboard, anything holding a request open while it sends nothing) and click around it: each page you leave ends its open request on the Site within a couple of seconds, so they no longer pile up there, on the Direct Path and through the Relay. A page that aborts its own fetch still leaves it open (#126). The service worker's part comes from the Relay: r.tooobs.net serves it already, and a Relay of your own needs redeploying.
- **[#3](https://github.com/Tooobs/tooob/issues/3) `tooob invites` shows readable expiry times** · 2026-11-06 · the next Release (not out yet)
  - `tooob invite blog jm`, `tooob invite blog dad --expires 40m` and `tooob invite blog mom --expires 5h`, then `tooob invites blog`: the EXPIRES column reads `in 7 days`, `in 40 minutes` and `in 5 hours` instead of a Unix timestamp. It rounds up, so it never says less time is left than there is: minutes up to 59, then hours up to 23, then days. `--json` still gives `expires_at` in Unix seconds, for scripts.
- **[#5](https://github.com/Tooobs/tooob/issues/5) A Host can be backed up and restored under a passphrase** · 2026-11-06 · the next Release (not out yet)
  - Put a passphrase in a file, then `tooob backup blog blog.backup --passphrase-file pass`: one file, readable only by you, with nothing in it you can read but its `tooob-backup` header. On another machine (or after `tooob rm blog`), `tooob restore blog blog.backup --passphrase-file pass` brings back the same Host: `tooob ls` and `tooob invites blog` show its Visitors and Invites, and its Invite Links still work, since its Host Key is the same. Try a wrong passphrase, a name that's taken, or restoring it beside the original: each is refused in one line saying what to type, and nothing is written. If its folder is somewhere else on the new machine, add `--serves PATH` (#127, below).
- **[#127](https://github.com/Tooobs/tooob/issues/127) A restored Host can serve its folder from another path** · 2026-11-06 · the next Release (not out yet)
  - On the new machine, `tooob restore blog blog.backup --passphrase-file pass --serves ~/Sites/blog`: `tooob show blog` says it serves `~/Sites/blog`, and `tooob run blog` serves it with the same Host Key, Visitors and Invites. `--serves` takes anything `tooob add` takes (a folder, a file, `HOST:PORT`) and refuses what it refuses, restoring nothing. Editing `serves` in the settings file by hand still won't run (a Host only ever serves what it first ran with, so Visitors invited to one folder never see another); the error now says to `tooob rm blog` and restore again with `--serves`.
- **[#113](https://github.com/Tooobs/tooob/issues/113) A Relay sends the Bootstrap compressed** · 2026-11-07 · the next Release (not out yet); live on r.tooobs.net now
  - Open an Invite Link through `https://r.tooobs.net/` in a fresh browser profile with DevTools' Network tab on: `web_bg.wasm` comes over as about 0.8 MB (`Content-Encoding: br`) instead of 3.1 MB, and on a phone-like connection the first visit's shell is up seconds sooner. Or `curl -sI -H 'Accept-Encoding: br' https://r.tooobs.net/__tooob/pkg/web_bg.wasm`. A Relay of your own (`deploy/`) does the same once redeployed: the image makes the brotli and gzip copies when it's built, so the Relay spends no CPU compressing, and the Bundle and its hashes don't change.

- **[#128](https://github.com/Tooobs/tooob/issues/128) A Relay forwards only traffic to or from an Enrolled Key** · 2026-11-07 · the next Release (not out yet); live on r.tooobs.net now
  - A Relay now runs tooob-relay, iroh-relay with one rule added: once it has any Enrolled Keys, it forwards a packet only if it comes from or goes to one of them, so strangers can't use it to talk to each other. With none, it's open, as before: `curl https://r.tooobs.net/__tooob/relay.json` says `{"relay_access":"open"}`. On a Relay of your own, redeploy, then `tooob-relay enroll <host key>` inside its container (`fly ssh console -C "tooob-relay enroll …"`; the key as `tooob invite` prints it before the Relay's domain): `relay.json` says `enrolled`, Visitors still reach that Host, and a Host you didn't enroll can't be reached through it. `tooob-relay list` and `remove` do the rest, and a removed key is cut off at once. Enrollment Codes, so an Owner can enroll their own Host, come next (#129).
- **[#129](https://github.com/Tooobs/tooob/issues/129) A Relay Operator makes Enrollment Codes, and a Host redeems one as it connects** · 2026-11-07 · the next Release (not out yet); live on r.tooobs.net now
  - A Relay Operator can make a code for an Owner instead of enrolling their key by hand: `tooob-relay code --label sam` inside the Relay's container (`fly ssh console -C "tooob-relay code --label sam"`) prints one such as `r.tooobs.net/7Q4K-M2XD-9PHT-WB3C`, good for one Host for 7 days (`--uses 3`, `--expires 30d` for more). `tooob-relay codes` lists the unused ones, and `cancel sam` cancels them. Only a hash of each code is kept in `/data`. A Host can't present a code yet: that's `--relay-code` (#132), and until then nothing shows from a Host's side.
- **[#130](https://github.com/Tooobs/tooob/issues/130) A Host tells its Owner when its Relay doesn't carry it yet, with the Host Key to hand over** · 2026-11-07 · the next Release (not out yet); live on r.tooobs.net now
  - A Host now asks its Relay whether it carries it. On a Relay that has Enrolled Keys but not this Host's, `tooob add` (and a `tooob share` that adds a Host) still succeeds, then says `<relay> doesn't carry this Host yet: give its Relay Operator this Host Key: <key>`; `tooob run` says it at start and in its log, and logs again when the Relay starts or stops carrying it; `tooob ls` shows it under the table and `ls --json` has `"enrollment"` (`open`, `enrolled`, `not_enrolled` or `unknown`), from the Host's last check. A Relay that can't be reached is never reported as not carrying it. On r.tooobs.net, which is open, nothing is printed and `ls --json` says `open`: `curl https://r.tooobs.net/__tooob/enrolled/<host key>` says `{"enrolled":false,"relay_access":"open"}`. To see the line, enroll some other key on a Relay of your own (`tooob-relay enroll …`).

## Still to come

What each later milestone will add when it's done, in the planned order. Details and progress: [the roadmap](https://github.com/Tooobs/tooob/blob/main/docs/roadmap.md).

### [Agents](https://github.com/Tooobs/tooob/blob/main/docs/roadmap.md#agents)

AI agents run Hosts for their Owners and visit Sites in a browser like anyone else. An agent shares a status dashboard or a preview with people and other agents by invitation, and every device its Invites let in is approved by a person first ([ADR 0018](docs/adr/0018-agents-make-approve-first-invites-enforced-by-agent-accounts.md)). A local MCP server lets an agent read, block and revoke; anything that would let someone in waits for the Owner.

### [Relay finder](https://github.com/Tooobs/tooob/blob/main/docs/roadmap.md#relay-finder)

Owners find a Relay to use instead of running their own: a plain list anyone can host, or a trusted site with each Relay's stats and terms, and an audit that checks what each one serves against tooob's published Releases. Choosing stays the Owner's.

### [Normal people](https://github.com/Tooobs/tooob/blob/main/docs/roadmap.md#normal-people)

tooob for people who don't open a terminal: a signed `tooob` for every Mac and for Windows that upgrades itself, set-up that walks them through it, and Visitors who keep working when a Host and its Relay's Bootstrap are a Protocol Version apart. Every v1 choice is already checked against it.

### [v2](https://github.com/Tooobs/tooob/blob/main/docs/roadmap.md#v2)

A native visitor app or browser extension, which reaches Hosts with iroh's own hole punching, friendly names in place of Host Keys, and linking a person's devices. Perhaps native phone apps too, so a phone can be a Host and a Site goes phone to phone.

### [Sync](https://github.com/Tooobs/tooob/blob/main/docs/roadmap.md#sync)

A folder kept in step across the Owner's devices and the people they invite, like Dropbox: a change made on any of them reaches the others. Its scope is still to be settled.

## Develop

- `./check.sh`: formatting, clippy, `cargo test`, the Bootstrap's build, the Bootstrap Bundle's manifest tests and `release.sh`'s tests (which need `npm ci` in `bootstrap/check` once); `git config core.hooksPath .githooks` (once per clone) runs it before every push.
- `test/linux/run.sh`: the Host's `cargo test` on Linux (musl), in [podman](https://podman.io) (`podman machine init && podman machine start` once on a Mac); arguments go to `cargo test` (`--test terminal`: one file).
- On every push to `main`, CI runs the Host's `cargo test` on Linux, on both targets the Linux Releases build (`x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl`), and nothing else: see [Linux tests](https://github.com/Tooobs/tooob/actions/workflows/linux-tests.yml) (`gh run list --workflow linux-tests.yml`). A red run there is a Linux breakage on `main`. Every other check runs locally.
- `./release.sh X.Y.Z`: cuts a Release from a clean, up-to-date `main` (`./check.sh`, the Host's tests on Linux through `test/linux/run.sh`, which needs podman running, the browser suite, the cross-Release check, then the Release number in both `Cargo.toml`s, `CHANGELOG.md`, a commit and its tag, pushed); CI then builds and publishes it. Add what each change does to `CHANGELOG.md`'s "Unreleased" as you go.
- The browser suite: end-to-end tests against real Hosts and a local Relay (tooob-relay, from `relay/`, which the suite builds), on [Playwright](https://playwright.dev), in Chromium, headless unless `HEADED=1`. Once: `cd bootstrap/check && npm ci && npx playwright install chromium`. Then `bootstrap/build.sh`, and in `bootstrap/check`, `npx playwright test` (one test: `-g '<name>'`; `HEADED=1 SLOWMO=500` to follow along in windows). A run can't take over the machine: one at a time, one worker, at most 4 tabs, 90 s a test and 15 minutes a run, and no Host or Relay it started outlives it, even if it's killed. `node --test guards.test.mjs` there tests those guards.
- `GLOSSARY.md` is the vocabulary, `DESIGN.md` the plan, and `docs/adr/` the decisions that are hard to reverse. `CLAUDE.md` is how we work, with or without an agent.
